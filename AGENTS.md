# AGENTS.md

Twitch HLS live-stream client (Rust) + `servermock/` (Node mock Twitch edge server) used to test it offline. No README; `todo.md` and `notes.txt` are the maintainer's live scratch notes — read them before touching scheduler/disk logic. `notes/` has the longer design documents (transport probe, slot arena / RTSP output, TLS client API).

## Commands

- Build/check: `cargo clippy -p twitch-hls-client2`, `cargo build -p twitch-hls-client2`
- Lint: `cargo clippy -p twitch-hls-client2 --all-targets` — Cargo.toml enables `pedantic`/`nursery`/`suspicious`/`cargo` groups as warn; keep it clean.
- Format: `crates/twitch/rustfmt.toml` uses **unstable** rustfmt options (`group_imports`, `imports_granularity`, `imports_layout`, `format_code_in_doc_comments`, `reorder_impl_items`) and pins LF; stable `cargo fmt` silently ignores them. Use `cargo +nightly fmt`.
- Tests: `cargo test -p twitch-hls-client2` (arena/spool, playlist/utils/variant parsing, and an HTTP client suite against a loopback mock server).
- Miri: `cargo +nightly miri test -p twitch-hls-client2` runs everything except the network tests (`cfg(not(miri))`); it is the check for the arena's handful of `unsafe` blocks.
- `servermock/unused/main_test.ts` is stale boilerplate — don't rely on it.

## Terminology

- **broadcast** — one Twitch channel's live stream. (Was "stream"; `stream_url` is the `manifest_url`, `stream_id` is Twitch's `BROADCAST-ID`.)
- **slot** — fixed 192 512 B zeroed buffer in the arena. Never "chunk": *chunk* means an HTTP transfer-encoding chunk.
- **segment** — one HLS media playlist entry (~2 s), one HTTP fetch.
- **spool** — the byte stream of one segment: one `Writer`, any number of `Reader`s, backed by a chain of slots.
- **consumer** — the task/sink reading a spool (RTSP, disk). A consumer owns one `ConsumerWake`.
- **reader** — a consumer's cursor into a spool.

## Local dev loop (servermock)

`--debug` mode bypasses Twitch and fetches `http://127.0.0.2:8000/index.m3u8`.

1. In `servermock/`: `pnpm install` first (installs `@node-rs/xxhash`); `pnpm dev` runs `node --watch main.ts`. It needs real segment files in `servermock/segments/` (gitignored, ~556 MB TS). Neither that directory nor `captures/` is ever copied into a worktree: the worktree startup hook runs `bash "$OPENCODE_WORKTREE_PATH/scripts/worktree-setup.sh"`, which hardlinks both from `$OPENCODE_WORKTREE_BASE` (`cp -al`), then runs `pnpm install`. The mock replays at `SPEED = 8` by default (override with `SPEED=1 pnpm dev` for a real-time RTSP test) and ends with `#EXT-X-ENDLIST`; `touch servermock/main.ts` restarts it from the top.
   - `captures/<channel>/<variant>/` holds `init.mp4`, ~2 s `.m4s` parts and the media playlist snapshot (`#EXT-X-MAP` + timings) for fMP4 work: `ledheadlive/1080p-h264` and `ledheadlive/1440p60-hevc` (HEVC is auth-gated on the usher; anonymous gets H.264). The mock does not read these.
2. `cargo run -p twitch-hls-client2 -- play -c anything -d` — `-c` is required by `play` even in debug mode; `daemon` takes the channel from the URI instead. Debug mode uses broadcast id `0`.
3. `play` serves RTSP on two loopback listeners on one port (`rtsp://127.0.0.1:7417/` and `rtsp://[::1]:7417/`; an ephemeral pair if 7417 is taken). `daemon` binds `--bind` (default `127.0.0.1:7417`) and serves `rtsp://127.0.0.1:7417/<channel>/<quality>/`; any channel and quality (or no quality for the first variant) creates a stream on DESCRIBE. RTSP is the only sink; disk and the raw-TS TCP fan-out are disabled/removed.
4. `ffplay -nodisp rtsp://127.0.0.1:7417/` and `ffprobe -rtsp_transport tcp -i rtsp://127.0.0.1:7417/` are the end-to-end checks (`.../sunnys/1080p/` under `daemon -d`).

## Architecture

Single-threaded `compio` reactor (`#[compio::main]`). Everything below runs as tasks on one thread, so there are no locks, no atomics and no `Send` bounds; threads exist only inside the driver (IOCP on Windows, io_uring on Linux). `!Send` tasks are deliberate — do not "fix" `clippy::future_not_send`.

- `arena.rs` — slot storage. Slots are allocation-free after startup; arenas are not, and that is deliberate.
  - **slots**: fixed `192_512` B (188 × 1024) zeroed slots, 32 per arena, intrusive refcounts where the `next` link holds a reference so a lagging reader can never follow a recycled slot. Arenas are `alloc_zeroed` and every view derives from one base pointer (Miri-checked under Stacked Borrows).
  - **arenas**: heap nodes in an intrusive singly linked list, so a middle node can be dropped without a table, plus a second singly linked list (the *free* list) of exactly the arenas with a free slot, so `alloc()` is O(1) and never scans. No `prev` links: `alloc()` only takes the head, and the only other removal is an arena emptying (once per 32 slot releases), so that path walks to the predecessor instead. `SlotId` is `{ NonNull<Arena>, u8 }` — the address *is* the id, so there is no id→arena table, and a live id implies a live arena (an arena is freed only when its last slot is released).
  - **the spare**: an emptied arena is kept, empty, as the single spare and consumed by the first allocation the free list cannot serve (a second spare frees the older one). Without it a pool at an arena boundary re-allocates 6 MB per slot. `arena_count()` counts the spare, so a full release asserts 1, not 0.
  - **no global cap**: `Arena::new` returns `None` rather than aborting, and the failure surfaces as `ArenaFull` like the per-segment cap, so a memory squeeze fails one segment.
- `spool.rs` — `Spool::open()` returns a `Writer`/`Reader` pair over `Rc<Spool>`, the merged writer block (`arena`, `published` total, `closed`); the writer plus every reader hold one `Rc` and the last of them frees it. There is no spool record table. `SEGMENT_SLOTS_MAX` (64 slots ≈ 12.3 MB, i.e. an 8 Mbps 10 s segment) caps one segment's spool and is the only `ArenaFull` source left. The writer appends into a slot tail and publishes; readers get owned, pinned `SlotView`s (`IoBuf`) that go straight to `write_all` / `write_at`, so the fan-out is zero-copy.
- **Wakeups**: a spool has no wait list. Each consumer task owns one `ConsumerWake` (one `Waker`, allocated once) registered in the scheduler's `WakeSet`; a publish wakes every registered consumer and each re-checks its own spool frontier. Never wait on a per-spool list — that was the old design and it also silently only completed on close.
- `http/` — hand-rolled HTTP/1.1 client. Pool keyed by `(tls, host, port)` with 4 idle/host, 8 total, 30 s; chunked-first framing decoder that reads payload straight into the caller's buffer; `rustls::unbuffered` driven over compio completion reads (no `compio-tls`, no futures-io bridge). rustls types are confined to `http/tls.rs`.
- `scheduler.rs` — polls the manifest through the client, parses Twitch tags, dispatches segment/prefetch/init fetches, fans spools out to registered consumers. `variant.rs` resolves master playlists via Twitch GQL + usher (`utils::query_string` percent-encodes the signed usher URL). Segment URLs are shared as `Rc<str>` between the fetch message and the prefetch entry. The registration channel is also the life signal: no senders left means the daemon dropped the stream, so the scheduler returns instead of waiting for a consumer that can never arrive.
- `daemon.rs` — the registry behind `daemon` mode. One `Client`, `ArenaSet` and downloader queue are global; `(channel, quality)` maps to a `Stream` pipeline (scheduler, `Dvr`, media engine, `WakeSet`, consumer-registration channel, stop flag). `DESCRIBE /<channel>/<quality>/` resolves the channel (one GQL variant fetch per login, cached while the channel has streams), picks the variant and builds the pipeline. The last control connection leaving stops the pipeline and drops the channel entry; `--max-streams` refuses a new stream with 503 and never evicts one someone is watching. Resolution is serialised per key by a small keyed async gate.
- `downloader.rs` — `constants::DOWNLOAD_TASKS` worker tasks pulling from a bounded queue; bodies stream into the spool; retries with backoff only while the spool is still empty (a retry after bytes would corrupt the segment).
- `rtsp/` — minimal RTSP server + ES-over-RTP output. `ts.rs` demuxes the TS source (PAT/PMT, PES, Annex B H.264, ADTS AAC), `h264.rs`/`aac.rs` are ports of gortsplib's RFC 6184/3640 packetizers, `sdp.rs` builds the description from discovered parameter sets. `vod.rs` ports twitch-dlp's `getM3u8.ts` to discover the full-broadcast playlist (public VOD through GQL + usher, otherwise the SHA-1 private DVR path) and keeps its parsed timeline fresh in a background task, in parallel with the live scheduler. `mod.rs` owns one media consumer, a pacer (1x live, 16x VOD into the bounded receiver queue), UDP or interleaved-TCP transports, RTCP SR, the RTSP control plane, and VOD seeking: a PAUSE+PLAY with a Range fetches DVR segments from the target keyframe and, at the DVR end, replays the scheduler's live playlist window up to the live edge. RTSP consumers join at the live edge (no backlog replay) so they cannot lag the pacer. `Stream` is one variant's RTSP presentation; a `Session` attaches to one on DESCRIBE (not on connect) and `StreamResolver` decides what a URI means (`play` serves one fixed stream, `daemon` goes through the registry).
- `disk.rs` — **disabled for now** (module not compiled). Would use `compio-fs` to append `manifest/{broadcast_id}.segs` and record-encode `manifest/{broadcast_id}.index` (magic `"OZENIKEN"`, version 3, little-endian). No file cursor: explicit offsets tracked in memory; the record buffer is reused. Restarts resume by reading the index once and replaying it.

No native FFmpeg dependency. The discontinuity probe is gone; `StreamRecord::Discontinuity` keeps its encoder/decoder so v3 index files stay compatible, and the init/SPS parser will produce it later (TODO in `disk.rs`). fMP4/HEVC/AV1 RTP output is not implemented yet.

## Gotchas (hard-won, do not "simplify")

- Twitch manifest parsing (`scheduler.rs::reload`): `#EXT-X-TWITCH-LIVE-SEQUENCE` appears multiple times during dropout protection; only the value immediately after `#EXT-X-MEDIA-SEQUENCE` (or after an ad segment) is trustworthy. `#EXT-X-TWITCH-ELAPSED-SECS` invalidates it. See `notes.txt`.
- The DVR playlist URL cannot be derived from the live variant URL. `rtsp/vod.rs` ports twitch-dlp's `getM3u8.ts`: try the public archive first (`FFZ_RecentBroadcasts` + `PlaybackAccessToken` + usher, only when the archive's `createdAt` is not older than the live stream's), then probe `{domain}/{sha1(vodPath)[..20]}_{vodPath}/chunked/index-dvr.m3u8` across `VOD_DOMAINS` for start offsets `0, -1, +1`. Use usher's `/vod/v2/` endpoint: it publishes the same `STABLE-VARIANT-ID` as the live master, and the archive's media playlist is picked by matching it. The master carries the playback signature; only its media playlist URLs are kept (they are unsigned and stable). The master is fetched in parallel with live variant resolution and only the choice is deferred. Debug mode uses the mock's fixed `/index-dvr.m3u8`. The parsed timeline is refreshed by a background task every 10 s (Twitch publishes a segment about that often), in parallel with the live scheduler; a seek never fetches a playlist first.
- mpegts ↔ fmp4 containers cannot cross disconnect protection (`notes.txt`).
- The index header is 24 bytes (magic + version + stream id); records start after it. Getting this wrong silently overwrites `stream_id` and breaks resume.
- A reader must be woken on **publish**, not only on close, or live streaming degenerates into one burst per segment. See `spool.rs::Wait`.
- `Reader: Clone` duplicates the cursor (same slot, same offset); it never rewinds. That is sound by construction — a clone copies a pinned cursor — but it means a clone taken after a partial read starts mid-segment. The scheduler's canonical readers (the window and the showing/backlog copies) are the only clone sources and never advance; do not reintroduce a `rewind()`/`head` API, and do not clone an advancing consumer's reader to "replay" a segment.
- `play` binds `127.0.0.1` and `::1` on the **same** port: v4 first (it resolves the port when `0` asks for an ephemeral one), then v6 on that number. They go through `socket2` (`TcpListener::from_std`) rather than compio's binder, which sets `SO_REUSEADDR` unconditionally — on Windows that lets a second process share a port instead of failing, so the ephemeral fallback would never trigger. Unix still sets it, to rebind over `TIME_WAIT`. `AddrInUse` on either family moves the whole pair to an ephemeral port; a family that cannot bind at all (IPv6 switched off) is skipped. Never bind `[::]` here: the wildcard is LAN-reachable, and loopback-only is the point.
- A completion read learns its size from the buffer's capacity; a fresh `Vec` needs `reserve` before `read`.
- Spans must be attached with `.instrument(span)`, never `span.enter()` held across an `.await` — everything shares one thread.
- `crates/twitch/src/index.hexpat` (ImHex pattern) mirrors `disk.rs`; keep both in sync when changing the on-disk format.
- Twitch's TS muxer does **not** align PES boundaries with access units: a PES can begin with the tail of the previous AU before the next AU's AUD. Treat the video PES payloads as one continuous Annex B stream and split at AUD NALs (`rtsp/ts.rs`); assuming one AU per PES drops ~20% of frames and corrupts every later reference.
- The RTSP playhead/NPT comes from the playlist's elapsed time (`Segment::timestamp_ms`), not from raw PES PTS (which is an arbitrary 90 kHz clock). DESCRIBE and PLAY both send an open-ended `npt=<playhead>-` range: the SDP range marks the stream live, and the PLAY range becomes ffmpeg's `range_start_offset` so clients can show absolute position. Prefetch segments are played over RTSP as well; their timestamp is extrapolated from the last complete segment because prefetch tags carry no elapsed time.
- RTCP fields are big-endian 32-bit words. `ntp >> 32` is still a `u64` in Rust, and the compound-packet length is words-minus-one; both mistakes silently shift the RTP/NTP mapping and make players report a DTS discontinuity.
- RTCP sender reports anchor the RTP/NTP pair on the **last packet actually sent**: `rtp` is its RTP timestamp and `ntp` is `origin + that packet's 90 kHz presentation time`, not the wall clock at send time. VOD is sent ahead of real time, so a wall-clock anchor would pull ffmpeg's SR mapping backwards on every report; a media-clock anchor makes the mapping identical between reports. Both tracks index the same shared PES base, so A/V sync is preserved. Never anchor on a separately computed DTS/playhead: ffmpeg's `delta_timestamp` must measure from a timestamp that is really on the wire.
- VOD playback fills the bounded per-session outbound queue and waits for capacity instead of dropping the client. That queue is the player's buffer: without it, a 2x player starves. The 16x pacer is throttled back to the client's drain rate by the queue, which also hides the next segment's on-demand fetch. Do not prefetch the next segment *before* the first emit: that made every seek wait for two full segments before sending a byte.
- The per-session outbound queue outlives a seek. Bump a per-session epoch on PAUSE/seek and have the writer drop older-epoch packets, or the queued live burst leaks into the new timeline. Additionally, hold the session (`Session::seeking`) from the PLAY response until `set_media_base` publishes the new RTP epoch: packets emitted in that window would otherwise carry the old sequence/timestamps into the new timeline. Keep the RTP **sequence** running across a seek: ffmpeg resets `s->seq` but keeps its RTP statistics (`max_seq`), so resetting to 1 looks like a 64k jump and produces `bad cseq 0001 expected=0001` before resynchronising. Continuing gives `max_seq + 1`, which is accepted immediately.
- The DVR playlist ends about one group (~10 s) behind the live edge, so jumping to the newest live spool skips that group. The scheduler publishes its live playback window (`Vec<Segment>`, Readers into the same spools) to the RTSP engine; at the handover the engine replays it from the DVR playhead (`position_ms`) up to the live edge at 4x, re-reading the window as it refreshes, then continues with the live consumer queue. Do **not** assume the queue contains the gap: a live-only consumer never receives segments published before it joined. Handover messages arrive out of order (a prefetch tag for the next segment can precede the main dispatch of the current one), so `push_handover` inserts by sequence and deduplicates; appending made the sequence filter drop the late segment and leave a 2 s hole.
- The RTSP consumer registers with `ConsumerRegistration { lossy: true }`. Its bounded queue fills during a slow VOD fetch or a download stall, and closing it (the old behaviour) permanently kills the output. A lossy consumer drops the individual message instead; normal live keeps only the newest segment and the DVR handover heals holes from the live window. The disk consumer stays strict.
- Never block the reactor thread. Everything shares one thread, so a *blocking* channel send is not "slow", it is a deadlock: the task that would free a slot can never be polled. Kanal's `Sender::send` parks the thread (`Signal::new_sync(..).wait()`), so `Session::out` is an `AsyncSender` -- it still has `try_send`/`len`/`capacity`/`is_closed`, but not the blocking `send`, so the deadlock is not writable. RTSP responses additionally go through `Session::control` (unbounded, drained by the writer before every message) and are poked with `try_send(Outbound::Flush)`, because a reply queued behind 4096 RTP packets still stalls the player's seek; `Outbound::Setup` and the fan-out use `try_send` too. The symptom was a hard freeze -- no RTP, no log lines at all -- whenever a seek arrived while the outbound queue was full, which is exactly what 16x VOD does.
- `try_send`'s "full" is not "closed". The fan-out used to `retain` only the sessions whose `try_send` succeeded, so one full queue (or one rejected RTCP report) silently unregistered a live client for good: the session task stayed alive and answered RTSP, but no packet was ever fanned out again until the player reconnected. `push_out` only unregisters on a closed channel, and `RTCP_HEADROOM` keeps slots free for the reports that are queued between samples.
- A daemon stream's life signal is its consumer-registration channel, not a poll. `StreamRuntime::stop` sets `Stream::stop`, stops the `Dvr`, pokes the scheduler's `ConsumerWake` and drops the registration sender: `next_reader`/`handle_new_readers` treat "closed and empty" as `Stopped`, so the scheduler returns instead of waiting forever for a consumer that can never arrive. `Stream::stop` also clears `seek_tx`, because that is the media engine's last sender and the only way to end its `recv`; `play_vod` and the media loop additionally check `stopped()` because a channel close cannot interrupt an in-flight VOD fetch. The watchdog checks it too, or it would hold the stream `Rc` for the process's life.
- A control connection attaches to a `Stream` on DESCRIBE, not on connect: the RTSP daemon counts viewers, and an idle OPTIONS connection must not keep a pipeline alive. `attach` moves a session between streams (`DVR` handover does not, but a second DESCRIBE legally can) and the cleanup in `control_session` releases the stream only when `has_sessions()` is false. `play` uses a `SingleStream` resolver whose `release` is a no-op, so it keeps serving after the last player leaves.
- Stream creation has no await between the capacity check and the insert (`spawn_stream` is synchronous), which is what makes `--max-streams` exact despite resolution running in several tasks. Regaining that property is easier than adding another lock. `ensure_capacity` first drops streams with no sessions; a stream someone is watching is never evicted.
- `Session::seek_started` gates the stream from the PLAY reply until `set_media_base`; the watchdog task releases the session after `SEEK_TIMEOUT` (and logs the state) if the seek never completes, so a broken seek degrades to a glitch instead of a stream that needs a reload. A watchdog line that never appears while a stream is silent means the thread itself is blocked or spinning, not waiting on the driver.
- The only polling in the tree is the HLS manifest poll. Everything else is event-driven: `Stream::wait_out_capacity` parks on `DrainSignal` (a generation counter plus one waker) instead of spinning on the queues. The RTSP writer bumps it after every dequeue, and pause/seek/`end_seek`/disconnect bump it too, because those change whether a session back-pressures the engine. The waiter re-checks after parking, so a notify cannot be lost; a missed notify is an indefinite stall, so add one wherever a session's `playing`/`seeking`/`is_closed` can change while the engine is parked.
- One RTP/RTCP packet is an `Rc<Vec<u8>>` shared by every session's queue: `Track::packet` builds it once per access unit and the fan-out is a refcount. Copying the packet per session per packet was ~20k allocations a second at 16x with two viewers. The interleaved-TCP writer keeps one framing buffer and hands it back through `write_all` (`BufResult.1`), so the four-byte header costs a copy but no allocation.
- Every panic is fatal (`main::abort_on_panic`): tasks are detached, so a panicking task would otherwise disappear silently -- the RTSP control plane keeps answering while no media is produced again. Release already aborts via `panic = "abort"`; the hook makes debug runs behave the same. `main` returns a `Result`, so a failed variant/manifest resolution exits non-zero instead of calling `process::exit` from inside the request path.
- A seek `PLAY` must omit `RTP-Info`. That header seeds ffmpeg's `base_timestamp`, but the media engine has not reset its RTP epoch yet when the PLAY response is built, so it advertises the old live timestamp. ffmpeg then rejects every post-seek packet until the next PLAY — the "click pause/play a couple of times to make the seek work" symptom. Without it the first packet establishes the base.
- On an RTSP seek the RTP/RTCP epoch must be reset together (`reset_media_base` + `Track::reset_mapping`), or the first post-seek sender report pairs an old RTP timestamp with a new NTP time. `media_delta` is signed: only a delta near ±2^33 is the wrap, because a small negative audio-vs-video offset is real (clamping it to zero makes frames share a timestamp). Anchor both tracks on the same minimum PES PTS of the first segment played.

## Repo conventions

- Colocated `jj` (Jujutsu) + git repo; git shows a detached HEAD. Work with `jj`, not git.
- jj workflow: open a new commit at the start of a task; commit each step and `jj squash` back down into it before moving on; `jj undo` recovers mistakes.
- Style: write efficient code — don't slow things down just to appease the borrow checker. Prefer fewer dependencies; `compio`, `rustls`, `http`, `httparse` and `futures-util` are the HTTP/runtime set.
- Prefer fixed-size storage when the bound is structural (slots, spool records, arenas); use a `Vec` only when the size is genuinely data-dependent (playlist window, consumer list), and pre-reserve it.
